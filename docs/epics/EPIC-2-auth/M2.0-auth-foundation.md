# M2.0: Better Auth foundation and client

## Goal
Rebuild the project’s Better Auth integration around the official Next.js pattern before relying on the existing auth forms or sign-out behavior.

## In scope / Out of scope
- **In scope:** inspect and correct the server auth configuration, Next.js catch-all route, client auth singleton, server session helper, and cookie configuration.
- **Out of scope:** auth UI redesign, password reset, social login, verification email, roles, or replacing Better Auth/MongoDB.

## Tasks
1. Read the official Better Auth Next.js, email/password, and session documentation linked from `EPIC.md`; confirm APIs against the installed dependency version.
2. Configure the existing Better Auth instance and MongoDB adapter without replacing the database/auth provider.
3. Ensure the Next.js catch-all API route delegates to `toNextJsHandler(auth)`.
4. Add the shared `authClient` with `createAuthClient` from `better-auth/react`.
5. Keep the `nextCookies()` plugin last if retained, and ensure the server session helper calls `auth.api.getSession` with awaited request headers.
6. Remove or replace incorrect manual auth endpoint calls only as part of the coordinated auth-flow reimplementation.

## Acceptance criteria
| AC | Testable binary statement | Verification method |
|---|---|---|
| M2.0-01 | Auth API catch-all delegates to Better Auth’s Next.js handler | Code inspection and API smoke test |
| M2.0-02 | One shared client is created with the official Better Auth React client API | Type-check and code inspection |
| M2.0-03 | Server session helper forwards request headers to `auth.api.getSession` | Code inspection and runtime check |
| M2.0-04 | Better Auth, MongoDB adapter, and cookie behavior match installed-version docs | Config review and runtime auth check |
| M2.0-05 | No duplicate auth endpoint implementation or Server Action has been introduced | Code inspection |

## Definition of Done
- Foundation matches the documented API for the installed Better Auth version.
- Lint, TypeScript, and production build pass.
- Runtime database/auth verification is recorded honestly as passed or blocked.
- Status updated in `STATUS.md`.
